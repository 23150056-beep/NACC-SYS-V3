# NACC SYS V3 — Cloud Deployment Guide

V3 runs as containers in the cloud. Nothing environment-specific is baked into
the image: the same artifact runs on a laptop, on staging, and in production,
and only environment variables differ.

Stack: Django 5.1 + Gunicorn · PostgreSQL (managed) · React (built static) ·
S3-compatible object storage for uploads · optional AI layer.

> Running on a single office PC instead? See [`DEPLOYMENT.md`](DEPLOYMENT.md) —
> the on-premises path is still supported and unchanged.

---

## 1. Architecture

```
        browser
           │
           ▼
   ┌───────────────┐        ┌──────────────────┐
   │  Static site  │──API──▶│  Django + Gunicorn│
   │ (React build) │        │   (container)     │
   └───────────────┘        └────┬──────┬───────┘
                                 │      │
                    ┌────────────┘      └──────────────┐
                    ▼                                  ▼
          ┌──────────────────┐             ┌────────────────────┐
          │ Managed Postgres │             │ S3-compatible bucket│
          │  (case records)  │             │ (reports, consents, │
          └──────────────────┘             │  child photos)      │
                                           └────────────────────┘
```

Two rules drive the whole design:

1. **The container filesystem is disposable.** Anything a container writes is
   gone on the next deploy. So uploads go to object storage and records go to
   managed Postgres — never to local disk.
2. **Secrets live in the platform, not in the repo or the database.** The
   Django secret key, database URL, bucket credentials, and AI API key are all
   environment variables held in the platform's secret store.

## 2. Deploy on Render (blueprint)

[`render.yaml`](../render.yaml) at the repo root declares the API service and
the frontend. **It does not declare a database** — see §2a.

1. Push this repository to GitHub.
2. Render → **New** → **Blueprint** → select the repository. Render reads
   `render.yaml` and creates both services.
3. Fill in the values Render marks as required (these are the `sync: false`
   entries — they are deliberately not in git):

   | Variable | Where it goes | Value |
   |---|---|---|
   | `DATABASE_URL` | API | the managed Postgres connection string (§2a) |
   | `AWS_STORAGE_BUCKET_NAME` | API | your private bucket name |
   | `AWS_S3_REGION_NAME` | API | e.g. `ap-southeast-1` |
   | `AWS_S3_ENDPOINT_URL` | API | blank for AWS S3; set for R2/B2/Supabase |
   | `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | API | bucket credentials |
   | `DJANGO_ALLOWED_HOSTS` | API | your custom domain, if any |
   | `VITE_API_BASE_URL` | Web | `https://<api-host>/api` |
   | `AI_HOSTED_API_KEY` | API | optional — leave unset to deploy with AI off |

   `DJANGO_SECRET_KEY` is generated by Render. `RENDER_EXTERNAL_HOSTNAME` is
   injected at runtime and the app appends it to `ALLOWED_HOSTS` and
   `CSRF_TRUSTED_ORIGINS` itself.

### 2a. The database lives outside Render

Render's free PostgreSQL instance is **deleted 30 days after it is created**,
data included. This deployment therefore uses [Neon](https://neon.tech)
(`ap-southeast-1`, PostgreSQL 16) instead, and `render.yaml` deliberately
declares no `databases:` block: if it did, a blueprint re-sync would rebind
`DATABASE_URL` to a Render-managed database and silently send writes somewhere
other than the live one.

Nothing in the application is tied to a particular host. `settings.py` parses
whatever `DATABASE_URL` it is given through `dj_database_url`, so any managed
Postgres works — Neon, Supabase, Aiven, RDS, or a Render paid instance.

Two settings that matter with a scale-to-zero provider like Neon:

- Use the **direct** connection string. A hostname containing `-pooler` routes
  through pgbouncer in transaction mode, which breaks Django's migrations.
- `DB_SSL_REQUIRE=true`, and keep `conn_health_checks` on (it is on by
  default). Neon suspends compute after a few minutes idle; without the health
  check Django would hand a request a pooled connection that died underneath it.

To move to a different provider later, restore a dump (§7) into the new host and
change `DATABASE_URL`. No code change is involved.

4. Deploy. The API's first boot runs migrations and seeds roles + the default
   administrator (`RUN_SEED=true`).
5. **Log in and change the default admin password immediately**:
   `admin@racco1.gov.ph` / `admin1234`.
6. Set `RUN_SEED=false` on the API service.

`VITE_API_BASE_URL` is compiled into the frontend bundle at build time, so the
web service needs a **redeploy** (not just a restart) whenever it changes.

## 3. Deploy anywhere with Docker

The images are plain Docker — nothing in them is Render-specific. The same two
`docker build` commands work for Railway, Fly.io, Cloud Run, ECS, or a VPS.

```bash
docker build -f backend/Dockerfile -t nacc-backend ./backend
docker build -f frontend/Dockerfile \
  --build-arg VITE_API_BASE_URL=https://api.example.org/api \
  -t nacc-frontend ./frontend
```

Then run the backend with, at minimum:

```
DATABASE_URL=postgres://...      DJANGO_SECRET_KEY=<50+ random chars>
DJANGO_DEBUG=False               DJANGO_ALLOWED_HOSTS=api.example.org
CORS_ALLOWED_ORIGINS=https://app.example.org
USE_S3=true                      AWS_STORAGE_BUCKET_NAME=... (+ credentials)
```

Point the platform's health check at **`/healthz/`**. It returns 200 only when
the app can reach its database, so a container with a bad `DATABASE_URL` fails
its deploy instead of quietly serving 500s to staff.

### Full stack locally

```bash
cp backend/.env.example backend/.env
docker compose up --build
```

Frontend on <http://localhost:5173>, API on <http://localhost:8000>. This is the
same image the cloud runs, against a real PostgreSQL — the fastest way to
reproduce a deployment problem.

## 5. Uploaded files: why S3 is not optional

Report PDFs, signed consent scans, and child photos are `FileField`/`ImageField`
uploads. On a container platform, the disk they land on is destroyed on every
deploy, restart, and scale event.

**A cloud deploy with `USE_S3=false` will silently lose uploaded case files.**
The database rows survive and point at files that no longer exist, so the loss
surfaces later as "File is missing from storage" on download.

Set `USE_S3=true` and keep the bucket **private**. The app never exposes
`MEDIA_URL`; files are served only through authenticated endpoints
(`/api/report-files/<id>/download/`, `/api/consents/<id>/download/`), which
stream the object through Django after checking the caller's permissions.

The only supported alternative is a persistent volume mounted at `MEDIA_ROOT`,
which limits you to hosts that offer volumes and to a single instance.

## 6. Data residency and RA 10173

This is the substantive change from V2 and it needs a decision on the record.

V2's Data Privacy Act posture was physical: the database, the uploaded files,
and the AI model all lived on one PC inside the RACCO I office. "Data never
leaves the building" was literally true.

**V3 moves that data to infrastructure the agency does not own.** The
compliance story therefore shifts from physical control to contractual control,
and the agency must have the following in place before real case data is loaded:

| Component | What it processes | What is required |
|---|---|---|
| Hosting platform | All case records | Data-processing agreement; a documented hosting region. |
| Managed PostgreSQL | All case records | Encryption at rest; access limited to the API service. |
| Object storage | Reports, consent scans, child photos | Private bucket; scoped credentials; encryption at rest. |
| Hosted AI provider *(only if enabled)* | Case text sent for summarization | A data-processing agreement covering it. **Not on by default.** |

Practical guidance:

- **Pick a hosting region deliberately.** `render.yaml` defaults to Singapore
  as the closest region to RACCO I; change it if the agency's policy requires a
  specific jurisdiction.
- **The AI layer is off by default and the system is fully functional without
  it.** Care-gap alerts are deterministic and never involve a model. If the
  hosted provider is not covered by an agreement, leave `AI_HOSTED_API_KEY`
  unset — nothing else changes.
- **Instrument copyright compliance is unaffected.** No instrument questions,
  scales, scoring keys, or norms are stored in V3 either; only titles and
  metadata.
- The Settings screen states which posture is active: on-premises shows
  "Private by design", hosted shows "Processed by a contracted provider".

## 7. Backups

The managed database and the object storage bucket hold everything. Both need
backups — a snapshot of one without the other restores to a broken system.

**Database.** Enable the provider's automated backups (daily, ≥ 7 days
retention). Take a manual dump before any release:

```bash
pg_dump "$DATABASE_URL" -F c -f "nacc_v3_$(date +%Y%m%d).dump"
```

Restoring into a *different* provider needs two extra flags, because the role
that owned the objects does not exist on the new host:

```bash
pg_restore --no-owner --no-privileges -d "$NEW_DATABASE_URL" nacc_v3_YYYYMMDD.dump
```

A `pg_dump` newer than the target server emits settings the server does not
recognise (`transaction_timeout` on a PostgreSQL 16 target, for example). Those
are session parameters; the restore reports them as ignored errors and the data
is unaffected. Verify by comparing row counts and
`SELECT count(*) FROM information_schema.tables WHERE table_schema='public'`
on both databases — never by assuming a silent restore worked.

A dump contains every case record and every password hash. Keep it outside the
repository working tree so it cannot reach a commit.

**Object storage.** Enable bucket versioning and a lifecycle rule, or sync to a
second bucket:

```bash
aws s3 sync "s3://$AWS_STORAGE_BUCKET_NAME" "s3://$BACKUP_BUCKET" --delete
```

Keep at least four rotations, in a location separate from the live
infrastructure — this is child data, and RA 10173 imposes a duty of care.

### Restore

```bash
# 1. Database
pg_restore --clean --if-exists -d "$DATABASE_URL" nacc_v3_YYYYMMDD.dump

# 2. Files — restore the bucket contents from the same date as the dump, or
#    the database will reference objects that are not there.
aws s3 sync "s3://$BACKUP_BUCKET" "s3://$AWS_STORAGE_BUCKET_NAME"
```

Rehearse a restore into a staging environment at least once per term. An
untested backup is not a backup.

## 8. Security checklist (per release)

- [ ] `DJANGO_DEBUG=False` and a unique 50+ character `DJANGO_SECRET_KEY`.
- [ ] `DJANGO_ALLOWED_HOSTS` restricted to the real hostnames.
- [ ] `python manage.py check --deploy` is clean (CI runs this on every push).
- [ ] HTTPS enforced; `SECURE_SSL_REDIRECT` on unless the proxy handles it.
- [ ] The media bucket is **private** and its credentials are scoped to it.
- [ ] The default admin password has been changed.
- [ ] `RUN_SEED=false` after the first deploy.
- [ ] Database backups are on, and a restore has been rehearsed.
- [ ] No instrument content in the database — spot-check
      `tbl_instrument_catalog` (titles/metadata only) and
      `tbl_agency_form_template` (attestation set).
- [ ] If the AI layer is on, the provider is covered by a data-processing
      agreement (§6).
- [ ] Access matrix below still holds after any permission change.

| Capability | Admin | Psychologist | Staff |
|---|---|---|---|
| Users / roles | full | — | — |
| Child & guardian records | full | read (assigned only) | create/edit |
| Terminate case (reason required) | yes | own cases | — |
| Instrument catalog / agency forms | all | own | — |
| Pre-assessment flow, remarks, plans, results, report uploads | yes | own children | read-only |
| Consent / interview / problem records | write | own children | read-only |
| Availability | all | own | read |

| Appointment status | yes | own | cancel only |
| Agency summary / census | yes | — (dashboard is scoped) | yes |

## 9. Google Sign-In (optional)

Staff and psychologists can sign in with a Google account instead of a
password. Administrators cannot, and this is deliberate: the admin account is
the agency's way back in, and tying it to a third-party identity provider means
a Google outage or a lost account locks RACCO I out of its own records.

**Signing in never creates an account.** An Administrator creates the user
first — correct role, with the person's Google address as their email — and
Google then replaces the password for that already-authorised account. An
unknown Google address is refused. For a system holding child case files, the
alternative ("anyone with a Gmail can get in") is not a door worth opening.

### Create the OAuth client

1. <https://console.cloud.google.com> → create or select a project
2. **APIs & Services → OAuth consent screen** → **Internal** if the agency has
   Google Workspace, otherwise **External**. Fill in the app name and support
   email.
3. **APIs & Services → Credentials → Create credentials → OAuth client ID**
   - Application type: **Web application**
   - **Authorised JavaScript origins**: your frontend URL, exactly, with no
     trailing slash — e.g. `https://nacc-v3-web.onrender.com`. Add
     `http://localhost:5173` too if you develop locally.
   - Authorised redirect URIs: leave empty. Google Identity Services returns
     the token to the page; there is no redirect leg.
4. Copy the **Client ID** (ends in `.apps.googleusercontent.com`).

### Configure the API service

| Variable | Value |
|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` | the client ID from step 4 |
| `GOOGLE_ALLOWED_DOMAINS` | optional, e.g. `racco1.gov.ph` — restricts sign-in to agency addresses |

Set these on the **API** service only. There is no client *secret*: the browser
flow uses an ID token the server verifies against Google's public keys, so
there is nothing secret to leak. **No frontend rebuild is needed** — the login
page reads the client ID from `/api/auth/google/config/` at runtime, so turning
the feature on or off is an API environment change alone.

### Enrol a user

1. Sign in as an Administrator → **User Management** → create the user
2. Set their **email to their Google address**, and the role to Psychologist
   or Staff
3. They open the login page and click **Sign in with Google**

First successful sign-in records Google's stable subject id against the
account. From then on matching is by that id, not the email — so a Google-side
address change can neither lock them out nor hand their session to anyone else.

### What is refused

| Situation | Result |
|---|---|
| Google address with no account here | Refused — an Administrator must create the account first |
| Administrator account | Refused — "use email and password" |
| Archived or deactivated user | Refused |
| Google email not verified | Refused |
| Address outside `GOOGLE_ALLOWED_DOMAINS` | Refused |

The first and third produce an identical message on purpose, so an outsider
cannot use the login page to discover which addresses belong to agency staff.

## 10. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Google button missing on the login page | `GOOGLE_OAUTH_CLIENT_ID` unset on the API | Set it; no frontend rebuild needed. |
| "Google Sign-In could not load" | Google's script is blocked (firewall, extension, offline) | Password login still works; the message is the intended fallback. |
| Google sign-in refused for a real staff member | No account here yet, or wrong role, or archived | Admin creates/fixes the account with their Google address as the email. |
| `origin_mismatch` / `idpiframe_initialization_failed` in the console | Frontend URL not in the OAuth client's Authorised JavaScript origins | Add it exactly, no trailing slash. |
| Container exits at boot with `ImproperlyConfigured` | `DJANGO_SECRET_KEY` unset with `DJANGO_DEBUG=False` | Set a real key. This failure is deliberate. |
| `DisallowedHost` in logs | Hostname not in `DJANGO_ALLOWED_HOSTS` | Add it. Render's own hostname is added automatically. |
| Frontend loads, every API call fails CORS | `CORS_ALLOWED_ORIGINS` missing the frontend origin | Add the exact scheme + host. |
| Infinite redirect loop | Proxy does not forward `X-Forwarded-Proto` | `SECURE_SSL_REDIRECT=False`. |
| Health check fails but the app looks fine | `/healthz/` can't reach the database | Check `DATABASE_URL`; add `DB_SSL_REQUIRE=true` for managed Postgres over the public internet. |
| "File is missing from storage" on download | Uploads went to an ephemeral disk | Set `USE_S3=true`. Files uploaded before that are unrecoverable. |
| API calls go to `localhost:8000` in production | `VITE_API_BASE_URL` not set at build time | Set it and **rebuild** — Vite inlines it into the bundle. |
| AI features return 503 | AI off, or no provider credential | Expected when off. Otherwise check `AI_HOSTED_API_KEY` and the provider in Settings. |
| Worker killed mid-AI-draft | `GUNICORN_TIMEOUT` ≤ `AI_HOSTED_TIMEOUT` | Raise `GUNICORN_TIMEOUT`. |
| Django admin CSS missing | `collectstatic` did not run | It runs at image build; check the build log. |
